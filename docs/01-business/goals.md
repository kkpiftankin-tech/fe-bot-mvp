# Цели

Измеримые результаты, ради которых строится FE-Bot. У каждой цели есть ID, однострочная формулировка и хотя бы один сигнал приёмки. Что именно система принимает и отдаёт — в [vision.md](vision.md#что-на-входе-и-что-на-выходе).

## Основные цели

### G-01. Сократить время до первого pipeline

**Формулировка.** Пользователь может пройти путь от однострочного описания ML-задачи до запускаемого пакета training pipeline в одной управляемой сессии (целевое значение: ≤ 15 минут wall-clock для эталонного сценария, см. [NFR-Perf-006](../02-system/non-functional-requirements.md)).

**Сигнал приёмки.**
- Для эталонного radar-сценария сквозной happy path производит `archive.zip`, содержащий `features.json`, `generation_spec.json`, `X_train.csv`, `y_train.npy`, `training_config.yaml`, `pipeline.py`, `metadata.json`.
- Wall-clock happy path фиксируется в `tests/e2e` и остаётся под целевым значением.

### G-02. Каждый артефакт прослеживается

**Формулировка.** Каждый признак, правило генерации, рекомендация модели и результат валидации прослеживается до исходного документа или RAG-карточки.

**Сигнал приёмки.**
- `FeatureSpec.evidence_doc_ids` непуст для каждого `approved`-признака.
- В [docs/traceability/](../traceability/) есть строка для каждого агента, контракта и семейства RAG-карточек.

### G-03. Детерминированная корректность важнее суждения LLM

**Формулировка.** Система никогда не полагается на строку LLM как на источник истины ниже по pipeline. Каждый вывод LLM парсится в Pydantic-схему и проверяется детерминированной проверкой.

**Сигнал приёмки.**
- Ни один агентный вывод не потребляется без успешной `model_validate`.
- [validators/](../../validators/) покрывают `ContextMemory`, `FeatureSpec`, `GenerationSpec`, сгенерированный датасет и RAG metadata.

### G-04. RAG поверх структурированной базы знаний, а не сырых blob-ов

**Формулировка.** Агенты читают из типизированных RAG-карточек с обязательной metadata, а не из свободного текста.

**Сигнал приёмки.**
- Каждая карточка в [rag/cards/](../../rag/cards/) проходит `validators/rag_metadata_validator.py`.
- RAG retrieval уважает per-agent, per-phase фильтры из [docs/06-rag/retrieval-policies.md](../06-rag/retrieval-policies.md).

### G-05. Синтетические данные производятся Python, а не LLM

**Формулировка.** LLM предлагает `GenerationSpec`; Python-worker строит датасет.

**Сигнал приёмки.**
- Ни один code-path не генерирует обучающие строки из токенов LLM.
- `validators/generated_data_validator.py` следит за отсутствием NaN/inf, балансом классов в допуске и соответствием схеме.

## Вторичные цели

### G-06. Маленькой LLM достаточно

**Формулировка.** `llama3.2:latest` через локальный Ollama — модель по умолчанию. Система обязана работать без проприетарных frontier-моделей.

**Сигнал приёмки.**
- Все prompt-eval тесты в [tests/prompt_eval/](../../tests/prompt_eval/) проходят на дефолтной Ollama-модели.

### G-07. Local-first, опциональное облако

**Формулировка.** Разработчик может поднять весь стек на ноутбуке через Docker Compose без внешних сервисов.

**Сигнал приёмки.**
- `make up-local-stack` поднимает систему на одном хосте без облачных credentials.

### G-08. Воспроизводимость каждого запуска

**Формулировка.** При заданных `ContextMemory` и `GenerationSpec` пакет байт-идентичен между запусками (с точностью до timestamps).

**Сигнал приёмки.**
- `random_state` обязателен в `GenerationSpec`.
- E2E-тесты проверяют, что повторный запуск экспорта производит идентичный hash `metadata.json` в части датасета.

## Цели стадий Setup и Analytics

Цели G-01..G-08 описывают главным образом Runtime и сквозные свойства. Две оставшиеся стадии получают собственные цели.

### G-09. База знаний собирается из документов за один сеанс мастера

**Формулировка.** Администратор базы знаний проходит путь от набора доменных документов до опубликованной базы знаний в одном сеансе Setup-мастера и видит на каждом шаге, что произошло и что требует его решения.

**Сигнал приёмки** (KPI MVP из [SETUP-01 §2.2](../02-system/features/SETUP-01-setup-wizard.md)):
- доля успешно обработанных документов ≥ 90 %;
- доля RAG-карточек с валидной metadata ≥ 95 %;
- доля chunks, успешно проиндексированных в Vector DB, ≥ 98 %;
- retrieval smoke test pass rate ≥ 80 %;
- время от загрузки документов до статуса `ready` ≤ 10 минут для малого корпуса;
- доля Setup-сессий, завершённых публикацией KB, ≥ 70 %.

Публикация невозможна, пока не пройдены retrieval smoke-тесты (см. [SETUP-10](../02-system/features/SETUP-10-retrieval-tests.md), [SETUP-11](../02-system/features/SETUP-11-publish-kb.md)); запуск Runtime без опубликованной базы знаний отклоняется ([RUNTIME-01](../02-system/features/RUNTIME-01-session.md)).

### G-10. Качество системы наблюдаемо

**Формулировка.** Product-owner и архитектор видят состояние обеих стадий на дашбордах без доступа к логам и базам, а любое решение системы можно проследить до исходного документа.

**Сигнал приёмки.**
- Счётчики воронки сессий совпадают с event-store без округлений ([ANALYTICS-01](../02-system/features/ANALYTICS-01-session-dashboard.md)).
- Для любого экспортированного артефакта audit trail доходит минимум до одного `source_document_id` и экспортируется как JSON ([ANALYTICS-09](../02-system/features/ANALYTICS-09-audit-trail.md)).

## Не-цели (для этой фазы)

- Обучение, хостинг и serving production-моделей.
- Облачное автоскалирование.
- Multi-tenant изоляция данных шире per-conversation скоупа.
- Streaming или real-time ML.
