# Правила prompt engineering

Целевая модель — маленькая локальная LLM (`llama3.2` через Ollama). Она быстрая, дешёвая и легко сбивается. Эти правила существуют, чтобы её выход надёжно потреблялся ниже по pipeline.

## Структура промпта

Каждый промпт в `prompts/` имеет эти разделы именно в таком порядке:

1. **SYSTEM** — роль, scope, формат вывода. Один короткий абзац.
2. **RULES** — пронумерованные жёсткие ограничения. Короткие, повелительные, тестируемые.
3. **INPUT** — помеченные плейсхолдеры для `ContextMemory`, `EvidencePack` и других структурированных входов.
4. **OUTPUT SCHEMA** — JSON-форма (ссылка по имени; сама схема подставляется в промпт во время сборки).

Agent runtime рендерит плейсхолдеры. Промпты — это текст под версионным контролем; никакой скрытой runtime-склейки.

## Жёсткие правила для авторов

- **Один агент, один промпт.** Никаких «сделай это и заодно вон то».
- **Только JSON**, где ожидается схема. Это указывается явно в `SYSTEM`.
- **Цитировать evidence.** Требовать `evidence_doc_ids`, когда агент читает RAG.
- **Отказываться при нехватке.** Сказать агенту возвращать `need_more_context: true` с конкретным уточняющим вопросом, если входа недостаточно.
- **Никакого chain-of-thought в выводе.** Рассуждение остаётся внутри модели; ответ — это схема.
- **Никакой прозы вокруг JSON.** Если в схеме есть поле `comment`, прозу пишут туда.

## Стиль

- Короткие предложения. Маленькая модель теряет длинные инструкции.
- Конкретные глаголы: «list», «select», «reject», «set». Избегать «consider», «think about».
- Имена полей цитировать буквально: `temporal_importance`, а не `temporality`.
- ALL CAPS использовать редко — только в секции RULES.

## Запрещённые паттерны

- **Few-shot примеры внутри промпта.** Примерам место в `tests/prompt_eval/`. Сам промпт — generic.
- **Смена языка.** Выбрать один (русский или английский) на промпт и держаться его.
- **Просить модель «быть осторожной» / «думать пошагово».** Заменить явными правилами.
- **Просить модель выдумывать недостающие данные.** Либо она цитирует evidence, либо возвращает `need_more_context: true`.

## Версионирование

- В каждом файле промпта во frontmatter лежит `prompt_template_version`.
- Изменение, меняющее форму вывода или правила, — это **major** bump; косметика — **minor**.
- Кейсы в `tests/prompt_eval/` ключуются по версии. Bump версии требует обновления или добавления кейсов.

## Repair Loops

Когда валидатор отверг вывод агента, runtime отправляет:

1. Исходный `INPUT`.
2. Предыдущий (невалидный) `OUTPUT` агента.
3. `ValidationReport` с конкретными ошибками.

Repair-промпт должен говорить: *«Исправь ровно перечисленные проблемы. Не меняй ничего другого.»* Это единственная ситуация, когда модель видит свой собственный предыдущий вывод.
