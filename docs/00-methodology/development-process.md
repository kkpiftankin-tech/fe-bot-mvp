# Процесс разработки

Эта страница определяет **порядок**, в котором артефакты появляются в репозитории. Порядок не подлежит обсуждению для нетривиальной работы; именно он держит маленькую LLM, агентов, RAG и код в согласованности.

## Конвейер

```text
Business Need
  → System Feature
  → Use Case
  → C4 Architecture
  → Agent Spec
  → ContextMemory Contract
  → RAG Ontology + Cards
  → Structured Output Schema
  → Prompt Template
  → Validator
  → LangGraph Node
  → Tests
  → Code
  → Docker
  → Observability
  → Runbook
```

Вывод каждого шага — это **входной контракт** для следующего. Пропуск шагов допустим только для тривиальных изменений (правки опечаток, мелкие правки docs) и никогда — для изменений, затрагивающих агентов, RAG или генерируемые артефакты.

## Поток на задачу

Для каждой задачи реализации:

1. **Прочитать контекст.** Открыть связанную фичу, use case, agent spec, схему и тесты. Если чего-то нет — остановиться и сначала написать.
2. **Сформулировать изменение.** Какие артефакты затронуты? Перечислить файлы. (Claude Code: подготовить план **до** правок.)
3. **Обновить docs.** Изменение существует в `docs/` раньше, чем в `src/`.
4. **Обновить контракты.** Если изменение пересекает границу агента — обновить Pydantic-схему в `schemas/`.
5. **Обновить или добавить тесты.** Тесты появляются раньше кода, который они охраняют.
6. **Реализовать.** Минимальное изменение, при котором тесты проходят.
7. **Запустить валидаторы и тесты.** См. [README.md](../../README.md#уровни-отладки) — лестница тестов по слоям.
8. **Обновить traceability.** Добавить или обновить соответствующую строку в `docs/traceability/`.

## Что считается «готово»

Задача готова, когда **все** условия выполнены:

- Соответствующие docs описывают новое состояние системы.
- Соответствующие контракты присутствуют в `schemas/`.
- Тесты на нужных слоях проходят: unit → component → integration → (rag_eval / prompt_eval где применимо).
- Валидаторы для затронутых артефактов проходят.
- В traceability-матрице есть строка про это изменение.

Задача **не готова**, если хоть одно из:

- Код агента существует без `docs/05-agents/<agent>.md`.
- На RAG-карточку ссылаются, но у неё нет metadata.
- Вывод LLM потребляется без Pydantic-валидации.
- Сгенерированные данные производятся token-генерацией, а не Python-инструментом.

## Работа с маленькой LLM

`llama3.2` — модель по умолчанию. Она маленькая и склонна к дрейфу. Чтобы быть надёжной:

- **Узкие промпты.** Один агент, одна фаза, одна output-схема, одно решение.
- **Передавать evidence, а не полные RAG-документы.** Агент видит `EvidencePack`, а не сырые карточки.
- **Валидировать перед потреблением.** Никогда не использовать сырую строку LLM ниже по pipeline.
- **Чинить, а не повторять вслепую.** При фейле валидатора отдать агенту отчёт валидатора и попросить починить конкретную проблему.
- **Фиксировать форматы.** Все выводы — JSON там, где ожидается схема. Без markdown внутри JSON.
